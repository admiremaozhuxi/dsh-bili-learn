# 设计与复盘：dsh-bili-learn

这份文档记录插件从一句需求长成一个可分发产品的过程：需求范围怎么划、设计上有哪些维度、重构做了什么、以及踩过的坑。

写给自己和接手的人。**不是功能介绍**——功能看 [README](../README.md)。这里只写「为什么这么做」和「哪里做错了」。

---

## 一、需求范围是怎么长出来的

### 1.1 起点

最初的需求只有一句：

> 「学习 B 站上前端的做法，帮我去做一个前端」

它包含三个隐含要求，后来都变成了功能：

1. **不是要链接，是要内容** —— 光给视频地址没用，得让 AI 读到里面讲了什么
2. **不是看一条，是看一类** —— 「B 站上前端的做法」意味着要搜、要挑、要横向对比
3. **读完要干活** —— 落地成「做一个前端」，所以内容必须落成文件，能被后续步骤消费

### 1.2 演化路径

需求不是一次说清的，是一层层加上去的。按时间顺序：

| 用户说 | 变成了什么 | 设计后果 |
|---|---|---|
| 「学习 B 站上的做法」 | 搜索 + 按播放量排序 | 只要高质量来源，不要随机视频 |
| 「AI 读不到视频」 | 字幕提取 | 需要登录态；实测覆盖率只有 ~11% |
| 「画面里也有东西」 | 抽帧 + 视觉模型 | 自动获取 ffmpeg；最低码率够读文字 |
| 「没字幕怎么办」 | 音频转写 | 不需要登录的兜底通道 |
| 「评论也算内容」 | 评论抓取 + 二级评论 | 需要 aid；翻页与 `ps` 上限的坑 |
| 「课程有几百集」 | 分P 清单 + 指定第几集 | 只读第一集等于没读 |
| 「一次读多条太片面」 | 多视频并行 + 子 agent 分配 | 队列 + worker 池模型 |
| 「不要 Python」 | 全 Node 实现 | 去掉外部运行时依赖 |
| 「能配置吗」 | 侧边栏面板 + 命令 | 11 项设置，单一规格表派生 |
| 「面板能一键保存吗」 | HTTP 路由（GET/POST） | 必须用 handler 路由，不能用 resource 路由 |
| 「没字幕就继续找下一个」 | 跳过 + 尝试上限 | `maxAttempts` 循环，默认 30 |
| 「转写和抽帧也要可控」 | 两个开关 + 上限 | 默认关闭，避免意外耗时 |

### 1.3 明确划出去的范围

**不做**这些，是有意的：

| 不做 | 理由 |
|---|---|
| 下载视频文件给你收藏 | 那是 `yt-dlp` 的活；这里只要「能读」 |
| 全自动过第三方站验证码 | 实测 13 个站纯 HTTP 请求全部不给直链 |
| 无登录拿字幕 | 实测无 cookie 时 `player/wbi/v2` 返回 `code=0` 但字幕数组为空 |
| 支持 B 站以外的平台 | 每个平台的签名、风控、字段都不同，混在一起会让代码失控 |
| 秒级问答 | 读一条无字幕视频要几分钟，定位是「研究」不是「检索」（这条后来写进了 README 的已知限制） |

## 二、设计维度

### 2.1 四条数据通道

一条视频的信息分布在四个地方，各自的获取成本不同：

| 通道 | 拿到什么 | 前置条件 | 成本 |
|---|---|---|---|
| 字幕 | UP 讲的原话 + 时间轴 | 登录（且该视频有字幕轨） | 低（一次请求） |
| 音频转写 | 没字幕时的口播全文 | 无 | 中（下载音轨 + ASR，约等于音频时长） |
| 抽帧 + 视觉 | 屏幕上的代码/PPT/界面 | 无 | 高（下载视频轨 + 每帧一次视觉调用） |
| 评论 | 观众反馈、补充信息 | 登录（否则只有 3 条预览） | 低 |

**设计后果**：不能只做一条。字幕覆盖率实测只有 11%，只做字幕等于对 89% 的视频无解。所以做成「有字幕走字幕（快），没字幕按开关决定转写/抽帧（慢但一定有）」。

### 2.2 取数限速与阅读并发必须分开

这是整个架构最重要的一条分界线。

- **取数**（打 B 站接口）受 IP 风控限制：实测同一 IP 约 30 次请求开始返回 412。加线程不会更快，只会更快撞墙。
- **阅读**（子 agent 读本地 md 文件）不受限制，可以并行。

所以：

```
取数：串行 + gapMs 间隔（默认 1200ms）+ 失败退避
阅读：并行 fan-out，按内容长度分配 agent
```

**如果混为一谈**，就会出现「开 8 个 agent 结果 8 倍速把 IP 送进冷却」——这个错误在早期版本里真实发生过。

### 2.3 并发模型：队列 + 固定 worker 池

多视频并行时有个矛盾：短视频内容少，给太多 agent 浪费；长视频内容多，给太少读不完。

采用「所有段落进一个队列 + 固定大小的 worker 池」：

```
短视频 A（2 段） → 用 2 个 worker
短视频 B（2 段） → 用 2 个 worker
超长课 C（8 段）  → 用 8 个 worker（超过「每片 2-4」的配置上限）

worker1: A#1 → C#3    ← A 读完后，这个 worker 自然去领 C 剩下的段落
worker2: A#2 → C#4
...
```

好处是**不需要额外的调度逻辑**：短片任务少，做完自然去队列里领长片剩下的段。

两条保证：

- 单个视频实际动用的 agent **可以超过**「每片分配」的上限（靠别片空出来的 worker 补）
- 同时在跑的总数**永远不超过**「总数上限」

段落数按字幕行数估算：`ceil(lines / 400)`，并以 `max*2` 封顶，避免超长视频把池子抽干。

### 2.4 配置体系：单一规格表

11 项设置，最初分散在十几处：默认值、view 返回、POST 校验、工具参数描述、面板 state、加载、保存、UI。

**加一个设置项要改 13 个地方，漏一处就是静默 bug**（前端拿不到值、或者写进去不生效）。

改成从一张规格表派生：

```js
export const SETTING_SPECS = {
  videoConcurrency: { kind: 'int', lo: 1, hi: 12, dflt: 3 },
  fillByTranscribe: { kind: 'bool', dflt: false },
  // ...
}
```

默认值、面板视图、写入校验、命令层范围全部从这张表算出来。**加一项只改一行。**

唯一保留手写的是 `bili_config` 的参数描述——那是给模型读的措辞，不适合从规格生成。

这个改动顺带修掉一个真 bug：面板读设置时手写字段列表，漏了 5 个字段（`fillByTranscribe` / `transcribeCap` / `fillByFrames` / `framesCap` / `framesPerVideo`），导致保存成功但重开面板变回默认值。

### 2.5 失败的四级降级

外部接口不可控，所以每一步都有退路：

| 层级 | 情况 | 处理 |
|---|---|---|
| 1 | 自己配置的解析服务器不可达 | 自动回落直连，报告里说明 |
| 2 | 直连签名接口失败 | 换普通接口并行竞速 |
| 3 | 视频没有字幕轨 | 按开关：跳过继续找下一个 / 音频转写 / 抽帧 |
| 4 | 单个视频彻底失败 | 记入 `skipped`，不中断整批，继续下一个直到 `maxAttempts` |

**关键原则**：降级要如实报告，不能假装成功。所以返回值里有 `mode` / `subtitleTrace` / `skipped` / `transcribed` / `framed` 这些字段，render 时直接展示「其中 1 个没有字幕轨，已用音频转写补上」。

### 2.6 落地形态

| 形态 | 用途 | 设计考虑 |
|---|---|---|
| 8 个工具 | AI 主动调用 | 每个工具只做一件事，名字即语义（`bili_watch` 看一条、`bili_series` 看系列） |
| 侧边栏面板 | 人改配置、扫码登录 | 侧边栏槽 + 主视图两个位置，不抢占别处 |
| `/bili` 命令 | 快速改单个设置 | 参数范围从规格表派生，不手写 |
| HTTP 路由 | 面板读写设置 | **必须用 handler 路由**（见教训 4.6） |

## 三、架构演进

三个阶段，每次的目标不同。

### 3.1 第一阶段：消灭重复定义

**动机**：加一个设置项要改 13 处。

**做法**：抽出 `SETTING_SPECS`，其他全部派生。

**结果**：index.js 2122 → 2089 行（几乎没变），但**加设置项的成本从 13 处降到 1 处**。

**这一阶段的真正收益不是行数**。

### 3.2 第二阶段：提取纯函数（Phase 1）

**动机**：index.js 2374 行，其中大部分是能被单独测试的逻辑。

**做法**（参照 Prisma 的模块化重构指南）：先提取无副作用的纯函数。

```
lib/specs.js   95 行   规格表 + 派生 + 校验 + 摘要
```

**结果**：index.js 2374 → 2292 行。

**关键收益**：这些函数现在能脱离插件运行测试：

```bash
node --input-type=module -e "import('./lib/specs.js').then(m => ...)"
```

以前验证配置逻辑要重启 DSH 整个插件。

### 3.3 第三阶段：工具模块化（Phase 2）

**动机**：`registerTools()` 一个函数 **983 行**，8 个工具全挤在里面。

**做法**：每个工具一个文件，导出 `registerXxx(ctx, deps)`，依赖显式传入。

```
lib/tools/
  learn.js       90    study.js      239
  config.js     190    watch.js      161
  series.js     139    frames.js      98
  transcribe.js  88    sources.js     74
```

**结果**：`registerTools()` 983 → 46 行，index.js 2292 → 1366 行。

**副作用**：依赖从「闭包随手可用」变成「必须显式声明」，这让隐藏依赖暴露出来——也是三次翻车的原因（见 4.1）。

### 3.4 行数的真相

| 阶段 | index.js | 仓库总行数 | 结论 |
|---|---|---|---|
| 起点 | 2122 | ~2600 | — |
| 规格表统一 | 2089 | ~2600 | 行数几乎不变 |
| 纯函数提取 | 2292 | ~2387 | **总量反而增加 13 行**（新文件有注释和 import/export） |
| 工具模块化 | 1366 | ~4450 | 总量继续增长 |

**总行数一直在涨，包含注释、文档、拆分成本。**

真正的进步指标不是行数，而是：

- 加一个功能要改几个文件
- 改一处逻辑要重启几次才能验证
- 出问题时能不能只看一个文件就定位

## 四、教训（按代价从高到低）

### 4.1 拆模块连翻三次车，同一个根因

**代价：三轮重启 + 两次"以为成功其实坏了"**

| 次数 | 丢了什么 | 怎么暴露的 | 为什么检查没抓到 |
|---|---|---|---|
| 1 | 文件头注释 | 语法错，立刻 | — |
| 2 | `const BUILTIN_SOURCES` | 调用 `bili_sources` 时报 `is not defined` | 它夹在最后一条工具注册和下一个 `function` 之间，被"到下一个顶层函数为止"的范围切走 |
| 3 | `mkdir` / `path` / `readFile` | 调用 `bili_watch` 时报 `is not defined` | 这些是 Node 内置，在原文件里是环境自带的，看着免费，搬到新文件就没了 |

**根因**：拆模块时只统计了「需要哪些**项目内**符号」，漏了另外两类：

1. **夹在删除范围内的顶层定义**（常量、注释块）
2. **Node 内置模块**（`mkdir`、`path`、`readFile`）

**后果的严重性**：`node --check` 只保证能解析，**不保证能跑**。引用不存在的变量在 JS 里是运行时错误，静态检查看不见。

**修复与防线**：

- 拆之前 `grep` 出范围内的**所有**顶层定义（`^function |^const |^let |^/\*\*`）
- 统计两类依赖（项目内符号 + Node 内置），两类都要跟着走
- 拆完用 mock ctx 跑一遍注册链路
- **最后必须真的调用一次那个工具**

完整清单见 [REFACTOR-CHECKLIST.md](REFACTOR-CHECKLIST.md)。

### 4.2 接口上限必须实测，不能信"通用值"

**代价：一个功能静默失效**

`x/v2/reply` 的 `ps` 参数，代码里按「上限 49」处理。实测：

```
ps=20  → code=0，返回 20 条
ps=40  → code=-400，返回 0 条
```

**真实上限是 20。**

后果：`commentPages: 2` 时 `limit` 算出 40，直接请求被拒，而第一页就报错，后面的翻页循环根本没机会跑——最终返回「评论 0 条」。

**为什么测试没发现**：默认 `limit=20` 恰好在上限内，只有多页请求才会越界。基础调用一直是通的。

**修复**：把 `ps` 钳到 20，多出的量走 `pn` 翻页（循环本来就有）。

**教训**：**参数上限要用边界值实测**，尤其是"看起来能一次拿很多"的分页参数。测 `ps=20` 和 `ps=40` 只要两次请求。

### 4.3 异步工具的返回值不是完整结果

**代价：工具把原始 JSON 直接吐给用户**

`bili_study` 派子 agent 研读，但 DSH 的 `subagent` 是**启动即返回**的——真实正文通过完成通知异步送达。

早期实现把工具调用结果直接 `JSON.stringify` 输出，用户看到的是：

```json
{"kind":"activation","callId":"..."}
```

**双重原因**：

1. 没有识别「这是 activation 结果」而不是正文
2. 即使识别了，`result` 外面还包了一层 `{callId, result}`，取值时没解包

**修复**：先解包（`raw?.result ?? raw`），再判断类型，最后给出人话说明：

> 已派出 1 个子 agent 研读，但它们的结果要异步回来，不会出现在本次返回里。文件都在 `...`。可等它们各自回报后再合并；或直接读取这些文件自己总结。

**教训**：异步工具的返回值要明确告诉用户「现在有什么、还差什么、下一步怎么办」，不能把框架的内部结构暴露出去。

### 4.4 可变状态传进模块会失效

**代价：一个工具永远读旧数据**

`probeAll()` 更新来源探测结果时是**整体重新赋值**：

```js
let sourceState = { at: 0, items: [] }
sourceState = { at: Date.now(), items: results }   // 换了个新对象
```

把 `sourceState` 传进 `lib/tools/sources.js` 后，模块手里那份永远指向旧对象。

**修复**：改成改字段。

```js
sourceState.at = Date.now()
sourceState.items = results
```

**教训**：跨模块共享的可变状态，**只能改字段，不能重新赋值**。

### 4.5 配置读取手写字段列表，必然漏

**代价：保存成功但重开变回默认值**

第一阶段之前，面板读设置时手写了字段列表，漏了 5 项。表现是：改了「没字幕时转写」的开关，点保存，接口返回 200，重开面板又变回关闭。

**修复**：从规格表派生（见 2.4）。

**教训**：**同一个信息只允许写一次**。手写列表 + 派生数据共存时，漏字段是时间问题不是概率问题。

### 4.6 DSH 的 HTTP 路由分两种，方法支持不同

**代价：面板保存功能整个不可用**

`webServer` 注册路由有两种：

- **resource 路由**：只应答 GET/HEAD，其他方法在匹配前就被 405 拒绝
- **handler 路由**：`handler: async (req, res)`，能拿到 Node 原生对象，支持任意方法

面板保存设置是 POST。用 resource 路由注册，永远 405。

**修复**：改成 handler 路由。修复后自检文件里 `postStatus: 200, postOk: true`。

**教训**：框架声称"支持某个能力"时，要看**具体是哪一种 API 提供的**。同名接口的两种变体，能力可能完全不同。

### 4.7 npm 首次发布有 10–17 分钟"假失败"窗口

**代价：浪费一个版本号 + 两次误判**

`npm publish` 输出 `+ dsh-bili-learn@0.2.0` 之后，registry 上只有：

```
versions: 0.0.0-stage
description: "Temporary package placeholder for staged publishing"
```

**这不是 staged release**——`npm stage list` 是空的，没有任何东西需要批准。只是**首次发布新包名的处理窗口**，真实版本要等 10–17 分钟。

**我当时的错误**：以为失败了，重发 0.2.1。结果两份都进了队列，最后两个版本都上线。

现在版本史里还留着：

| 版本 | 状态 |
|---|---|
| 0.2.4 | latest |
| 0.2.3 | 正常 |
| 0.2.2 | 正常 |
| 0.2.1 | 正常，但没带 engines 声明 |
| 0.2.0 | 已 deprecated（窗口期重复提交） |
| 0.0.0-stage | 已 deprecated（占位） |

**教训**：发布后**等 10 分钟再判断成败**，用 `npm view <pkg> versions --prefer-online` 绕缓存。不要在窗口期内重发。

### 4.8 文案不能比真实能力跑得快

**代价：差点写出会被打脸的卖点**

中间一度想把定位写成「下一个必应/百度」。这个类比有问题：

- 搜索引擎的隐含承诺是**秒级**
- 这个插件读一条无字幕视频要**几分钟**，读 8 条并汇总要**十几分钟**

如果真这么写，用户敲个问题等三分钟就会觉得被骗。

**最终采用的切角**：打搜索引擎的**盲区**，而不是替代它。

> 搜索引擎索引网页。它索引不到视频里的声音，也索引不到屏幕上的操作。

同时把耗时摊开写在「已知限制」里，先承认再说用法：

> 所以它的正确用法是**"研究"而不是"检索"**：你带着一个具体问题来，让它把这块视频内容读透、给出结论。

**教训**：**先承认限制，反而更容易被信任**。给技术用户写文案，任何夸大都会被第一条评论拆穿。

### 4.9 从 B 站学到的东西，在评论区而不在正文

**代价：无，但有意外收获**

为了优化文案去采了 4 条高播放的「DSH 必装插件」视频（合计 200 万播放）。正文教的是推荐套路（数量级痛点 → 一句话能力 → 场景演示），但**真正的信息在评论区**：

| 评论 | 赞 | 暴露的恐惧 |
|---|---|---|
| 「插件能不能卸干净、装一起会不会互相拆台，比清单长度值钱」 | 119 | 卸载 + 冲突 |
| 「装了其他插件，再装这 4 个，直接崩溃了……大家千万别装」 | 10 | 装完崩了 |
| 「刚装 DSH0.20 的注意，许多插件还没适配」 | 84 | 版本不兼容 |
| 「dsh-whale-widget 好看，但它读凭据、代码里还有云元数据 IP」 | 76 | 凭据安全 |

于是 README 加了一节「装机注意」，正面回答这四个恐惧：engines 声明、只占两个 slot、卸载只删一个目录、凭据只存本地且代码 76 行可审。

**另一个发现**：评论区大量 AI 生成的水军回复，**真人实测内容反而稀缺**。所以 README 里那节「实测结论（12 条带证据的接口行为）」是差异化优势，一个字没改。

**教训**：想看用户真实关切，看评论区；想学表达套路，看正文。
